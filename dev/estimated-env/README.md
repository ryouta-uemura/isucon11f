# 推定稼働環境のつくりかた

ローカルの Mac に「本番(競技)環境の代わりに観察してよい環境」を、毎回同じ手順で組み立てるための方法論。
目的は本番の再現ではなく、**どの結論なら本番に持ち帰れるかを先に宣言した模型をつくること**。

スコアを測る道具の話ではない。環境を定義し・組み立て・それが前提どおりであることを確かめ・
結論の有効範囲を限定するまでが対象。

---

## 原則

1. **モデルを先に書く。** 環境はコードではなく宣言から組み立てる。入力は [`env-model.yaml`](./env-model.yaml) ただ一つ。
2. **事実と仮定を混ぜない。** モデルの各値には出典 (`source:`) か仮定フラグ (`assumed: true`) を必ず付ける。
   仮定が結論を左右したら、そこが次に検証すべき場所。
3. **忠実度は目的ごとに違う。** 全部を忠実にはできない。何を捨てたかを台帳 (§4) に書き、
   捨てた軸に依存する結論は「この環境では判断不能」と明示する。
4. **環境は毎回同じとは限らない。** 同じ Mac でも熱・他プロセスで変わる。
   組み立てるたびに校正 (§3) し、前回と比べてズレていたらその回の観察は捨てる。
5. **環境の変更と webapp の変更は同じコミットに入れない。** 混ざった瞬間に差分の因果が追えなくなる。

---

## S1. 一次情報を抽出してモデルに固定する

`provisioning/` と `benchmarker/` から環境仕様を読み出し、`env-model.yaml` に出典付きで書く。
すでに抽出済み。**再抽出が必要なのは `provisioning/` か `benchmarker/score/` を含むコミットを取り込んだときだけ。**

抽出結果のうち、ローカルを組むときに効く非自明な点:

| 項目 | 本番 | 効いてくるところ |
|---|---|---|
| 競技者サーバ | c5.large × 3 (2 vCPU) | app/mysql/nginx が 2 vCPU を取り合う |
| 実効メモリ | **2GB** (GRUB `mem=2G`) | 公称 4GiB ではない。メモリを使う改修の可否がここで決まる |
| MySQL | 8.0 / 設定は charset のみ | **buffer pool 128MB、`sync_binlog=1`、binlog ON** のまま |
| sysctl | **未チューニング** | somaxconn 等は Ubuntu 既定。高並列時の accept queue が本番の律速 |
| nginx | TLS 終端 + 静的配信 + http2 | TLS/静的のコストは競技者サーバ持ち。upstream keepalive なし |
| ベンチ | c5.xlarge (4 vCPU) の別インスタンス | **負荷側の方が CPU が多い**。同居させると前提が壊れる |
| 初期データ | 660KB | 初期サイズではなく負荷中の増加分が効く |

出典は `env-model.yaml` の各 `source:` を参照。

## S2. モデルをローカルへ写像する

3 つのプロファイルを使い分ける。**プロファイル名を書かない観察結果は無効**とする運用にする。

| | P1 `correctness` | P2 `resource` | P3 `topology` |
|---|---|---|---|
| 狙い | 壊れていないかだけ見る | 資源制約下の振る舞いを見る | 台数構成の判断をする |
| CPU/メモリ制限 | なし | **2 vCPU / 2GB を1コンテナに同居** | 2 vCPU / 2GB × 3 |
| MySQL 設定 | 既定 | **ansible の my.cnf をマウント、buffer pool も既定のまま** | 同左 |
| nginx | あり/なしどちらでも | ansible の nginx.conf + TLS | 同左 |
| 負荷元 | 手で叩く | 同一ホスト (前提が崩れている自覚を持つ) | 同左 |
| 組み立て | `dev/docker-compose-go.yaml` のまま | 下記の写像規則に従って別 compose を起こす | 同上 |
| 言えること | API が壊れた/直った | メモリ・I/O・コネクション起因の改善 | 分散構成の是非 |
| 言えないこと | 性能のことは何も | 絶対スコア、飽和点 | 同左 |

写像規則 (P2/P3 を起こすとき):

- **設定ファイルは書き写さずマウントする。** `provisioning/ansible/roles/contestant/files/...` の実物を
  そのまま bind mount する。コピーした瞬間に本番と乖離し、乖離に気付けなくなる。
- **イメージはダイジェストで固定する。** 現在の `dev/docker-compose-go.yaml` は `image: mysql` (タグなし) で、
  引く日によって別物になる。推定稼働環境では `mysql:8.0.x@sha256:...` まで固定し、モデルの
  `contestant.mysql.version` と一致させる。
- **資源制限は必ず付ける。** `cpus: 2.0` / `mem_limit: 2g`。これを忘れた環境は P1 であって P2 ではない。
- **CPU アーキテクチャは arm64 ネイティブのままにする。** `platform: linux/amd64` にすると
  エミュレーションで 5〜10 倍遅くなり、遅さの原因がコードか翻訳かを分離できなくなる。
  amd64 との差は §3 の係数に押し込む。
- **ホストのポート衝突を先に潰す。** この Mac では 3306 に native な mysqld、7000 に macOS の
  ControlCenter が居る。推定稼働環境はホストへ 1 ポート (8080) だけ出し、内部は compose ネットワークで閉じる。

## S3. 校正する (ここが再現性の本体)

ローカルの絶対性能は本番と違う。違いを **スカラー係数 k** 一つに押し込み、観察値は常に k で正規化してから比較する。

環境を立てるたびに、**同じ 3 つのプローブ**を取って `calib/<YYYYMMDD-HHMM>.json` に保存する:

| プローブ | 測るもの | 取り方の例 |
|---|---|---|
| CPU 単体 | シングルコア速度 | 固定ワークロードを 1 スレッドで既定回数 (毎回同じコマンド・同じ引数) |
| MySQL 往復 | クエリ 1 本のコスト | PK 1 件 SELECT を N 回、接続は使い回し |
| fsync | コミットのコスト | 小さい INSERT を autocommit で N 回 |

運用規則:

- k = (今回のプローブ値) / (基準プローブ値)。基準は最初に取った回を `calib/baseline.json` として固定する。
- **k が基準から ±10% を超えて動いた回の観察は捨てる。** 熱・他プロセス・Docker VM の状態が違う。
- 比較する 2 つの観察は、**同じ日の、同じ baseline の下で**取る。昨日の数字と今日の数字は比べない。
- c5.large の基準値を一度でも実測できたら `calib/c5large.json` として置く。
  これがあると k が「本番換算係数」になり、ローカル値から本番の当たりが付けられる。無ければ k は
  「ローカル同士を比べるための正規化係数」止まり。それでも改善の有無の判定には足りる。

## S4. 忠実度台帳 — 何を捨てたか

写像で必ず壊れる前提と、それによって無効になる結論。**環境を変えたらこの表も更新する。**

| 非忠実点 | 本番 | ローカル | 無効になる結論 | 生き残る結論 |
|---|---|---|---|---|
| CPU アーキ | amd64 (Xeon) | arm64 (Apple Silicon) | 絶対スコア、命令レベルの最適化 | 計算量・クエリ回数の削減 |
| 仮想化 | ベアメタル相当の EC2 | Docker VM (Linux on HV) | I/O とシステムコールの絶対値 | I/O 回数の増減 |
| 負荷元の位置 | 別インスタンス (4 vCPU) | 同一ホスト | 飽和点、高並列時の挙動 | 低並列のレイテンシ、機能的な正しさ |
| ネットワーク | VPC 内 LAN | loopback / bridge | TLS ハンドシェイクと RTT のコスト | アプリ処理時間の差 |
| ディスク | gp3 (3000 IOPS) | Mac の NVMe + VM | fsync の絶対レイテンシ | fsync 回数の増減 |
| sysctl | Ubuntu 既定 | Docker VM の既定 | accept queue 起因の詰まり | それ以外 |
| メモリ 2GB | GRUB で強制 | **`mem_limit: 2g` で再現可能** | — | OOM / buffer pool 起因の挙動はそのまま移植してよい |

最後の行が重要で、**メモリ制約だけはローカルで忠実に再現できる**。
いま進行中の in-memory store 化のような「メモリと引き換えに速くする」改修は、
速くなったかはローカルでは判定できないが、**2GB に収まるかはローカルで判定できる**。

## S5. 状態をそろえる

性能の前に状態の再現性。観察を取る前に毎回:

1. `docker compose down -v` でボリュームごと捨てる (DB を使い回さない)。
2. 立ち上げ後に `POST /initialize` を叩く。これが唯一の初期状態の定義。
3. 固定の warmup を流す (page cache と接続プールの状態をそろえる)。回数・内容は毎回同じにする。
4. 校正プローブ (§3) を取る。
5. ここで初めて観察を取る。3 回取って中央値を使う。

## S6. 判定する

「改善が効いたか」は**一次指標**で判定し、推定スコアは二次指標として扱う。

- 一次指標 (環境非依存に近い): 発行クエリ本数、fsync 回数、レスポンスのペイロードサイズ、ピーク RSS、エラー有無。
  → ローカルで減っていれば本番でも減る。**これで判定する。**
- 二次指標 (環境依存): レイテンシ、スループット、推定スコア。
  → k で正規化し、3 回中央値の差が校正ノイズ幅 (§3 の ±10%) を超えたときだけ言及する。超えなければ「差は検出できなかった」。
- どちらも動かないのに速くなった気がする、は環境の状態ズレを疑う (S5 をやり直す)。

## チェックリスト

環境を組み立てたとき:

- [ ] `env-model.yaml` の `derived_from_revision` は現在の HEAD と整合しているか
- [ ] プロファイル (P1/P2/P3) を明示したか
- [ ] 資源制限 (`cpus` / `mem_limit`) が入っているか (P2/P3)
- [ ] 設定ファイルは ansible の実物をマウントしているか (コピーしていないか)
- [ ] イメージはダイジェスト固定か
- [ ] `calib/baseline.json` があるか、無ければ今回のを baseline にしたか

観察を記録するとき:

- [ ] プロファイル / k / 日付 / webapp の git rev を一緒に書いたか
- [ ] 一次指標を先に書いたか
- [ ] 忠実度台帳 (§4) で「この結論は有効か」を確認したか

## 現状の前提 (この Mac)

- Docker デーモンが停止している。Rancher Desktop の起動が必要 (`docker-compose` は `~/.rd/bin` にある v1 系)。
- ホストの 3306 は native mysqld、7000 は macOS ControlCenter が占有済み。
- `webapp/go` はビルドが通る。公式 benchmarker のビルドはモジュール取得が必要。

- `calib/baseline.json` — 校正の基準値
